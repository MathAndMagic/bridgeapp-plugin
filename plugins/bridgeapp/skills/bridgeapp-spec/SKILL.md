# Writing a spec

A spec describes how something works, so that whoever does the work can do it
without asking back, and whoever approves it can approve it without digging.
Nothing else goes in.

## Context first

Find out what was already decided before asking anything: the task, its
threads, older discussions nobody linked, existing documents, and any other
source you can reach — not only BridgeApp. Gathering the decision history is
what `bridgeapp-investigation` does; use it.

If a document on the same subject already exists, ask the author whether to
update it or write a new one.

## Ask

- **Contradictions** between sources, or between the request and an earlier
  decision: show both sides with their sources and let the author choose.
- **Additions** the context holds and the author did not mention: offer them,
  add only what they accept.
- **Gaps** that matter for doing the work: ask.

An open question goes into the document only if the author agrees to it.

## Write

- How it works, stated concretely enough to check. No instructions on how to
  build it, no filler.
- References next to the point they illustrate — screenshots, media, links to
  the source. One link at the top is not enough.
- Every statement comes from a source or from the author.

## Every time

After writing or changing the document, ask the author to read it carefully
before it goes to the task or to anyone else.

Reply in the user's language.
